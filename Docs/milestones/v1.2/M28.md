# M28 — Web saves (plan, 2026-10-16) — done (2026-10-16)

*Part of the 1.2 roadmap: [`Roadmap.md`](Roadmap.md). Where it fits: `../../GamePlan.md` §12; systems as built: §13
(Save / load, WebGL build); procedure: `webgl-build` skill.*

## Goal
Cities saved in the browser version are still there after a refresh, a closed tab and a new upload of the game, and a
player can keep a copy outside the browser.

## Cause (found while planning)
Saves are plain `File` writes under `persistentDataPath` (`SaveSlots`), which on WebGL is an in-memory Emscripten file
system backed by IndexedDB (`/idbfs/<hash>`). Writes reach IndexedDB only when the file system is synced; Unity's loader
does that only with `config.autoSyncPersistentDataPath = true`, which is **commented out** in the generated
`index.html` (`Build/WebGL/index.html` line 95). The live game is served by the site's own page,
`https://jpm20000.com/projects/city-game/play/` (it builds its own `config` and calls `createUnityInstance` with
`?v=` cache-busting on the build files), and that config does not set it either. So no save has ever been flushed:
everything lives in memory until the page goes away.

Cookies are not an option: one save is ~90 KB plus an ~85 KB thumbnail, and cookies hold ~4 KB and are sent with every
request. `localStorage` (~5 MB, strings only) would fit a handful. IndexedDB, which the game already uses, is right — it
just needs flushing.

The page path is stable across uploads (only the `?v=` on the build files changes), so the `<hash>` Unity derives from
the page URL stays the same and the save folder does not need moving.

## Done when
- In a browser build: save, refresh → the save is listed and loads; same after closing the tab, after an autosave, a
  rename and a delete; settings (`PlayerPrefs`) also persist.
- After uploading a new build to the site (new `BUILD_VERSION`), the saves from the previous build are still listed.
- Export (download a `.json`) and Import (pick a `.json`) work in the Load panel on WebGL.
- Desktop build behaviour and files unchanged (`-smokeTest` green); EditMode green; docs and `webgl-build` skill updated.

## Design decisions (answered 2026-10-16: host is jpm20000.com, ships in 1.2.0)
| Topic | Decision | Why / alternative |
|---|---|---|
| How to flush | A small `.jslib` (`ChronoSyncFs` → `FS.syncfs(false, …)`) called after every save-folder change and `PlayerPrefs.Save` — the game fixes itself whatever page loads it | Belt and braces: also add `autoSyncPersistentDataPath: true` to the site page's `config` (a one-line change in the website repo, not this one — done by hand when the 1.2 build is uploaded, see M31). |
| Save folder | Keep `persistentDataPath/Saves` (stable on this host) | A fixed `/idbfs/Chronopolis` folder is only needed if the page path ever changes; noted as a fallback, not built. |
| Export / Import | Yes, WebGL only, in the Load panel: download the selected save's `.json`; upload a `.json` and add it with `SaveSlots.UniqueName` | Browser storage is cleared with site data or in private windows; a file is the only real backup. |
| Thumbnails on WebGL | Kept | ~85 KB each, IndexedDB quota is hundreds of MB. |

## Architecture
- `Assets/_Game/Plugins/WebGL/ChronoFs.jslib`: `ChronoSyncFs()` (debounced: one `FS.syncfs(false)` in flight, a second
  request queued), `ChronoDownload(name, text)` (Blob + temporary `<a download>`), `ChronoPickFile(gameObject, method)`
  (hidden `<input type=file>`, `SendMessage` back with the text).
- `SaveSlots` (Simulation asmdef, stays pure): a static `Action Changed` hook raised after `Write`, `Delete`, `Rename`,
  `ImportFolder`, `ImportLegacy`. Runtime `WebStorage` (Assembly-CSharp, `#if UNITY_WEBGL && !UNITY_EDITOR`
  `[DllImport("__Internal")]`, no-ops elsewhere) subscribes and calls `ChronoSyncFs`; `GameSettings` calls it after
  `PlayerPrefs.Save`.
- Load panel: Export / Import buttons built at runtime under `#if UNITY_WEBGL` (desktop panel unchanged).

## Risks / open questions
- `FS.syncfs` is asynchronous: a tab closed in the same instant as a save can still lose it; the flush runs right after
  the write, so the window is small. A `beforeunload` sync is attempted but cannot be awaited.
- Players' current browser saves were never flushed, so there is nothing to migrate: they are already gone after a refresh.
- Private windows and "clear site data" still wipe saves; Export is the answer, and the Load panel can say so in a hint.
